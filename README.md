# Restaurant Guests Forecasting

Прогнозирование количества гостей ресторана на следующие дни
на основе исторических данных посещаемости, календарных признаков и информации
о ресторанах.

## Задача

Целевая переменная — `guests`: количество посетителей ресторана в конкретный день.

## Что сделано

- проведён EDA исходного датасета;
- восстановлен дневной календарь для ресторанов;
- добавлены временные, календарные, лаговые и rolling-признаки;
- проверены признаки на data leakage;
- выполнен временной train/validation split;
- построен baseline `lag-7`;
- обучены и сравнены LR, CatBoost, Random Forest и Prophet;
- качество моделей оценено на одном validation-периоде по MAE и RMSE;
- основная логика вынесена в переиспользуемые модули `src/`;
- подготовлен CLI для получения прогноза сохранённой моделью.

## Данные

Для задачи выбран датасет Kaggle **Recruit Restaurant Visitor Forecasting**.

Он подходит для задачи прогнозирования посещаемости, поскольку содержит
дневную историю посещений нескольких сотен ресторанов и охватывает период
более 12 месяцев: с 2016-01-01 по 2017-04-22. Всего в датасете около
829 ресторанов.

Исходный датасет состоит из трёх основных таблиц:

- `air_visit_data.csv` — фактическое количество гостей (`visitors`) для
  ресторана (`air_store_id`) по датам;
- `air_store_info.csv` — характеристики ресторана: жанр и район;
- `date_info.csv` — календарная информация, включая праздничные дни. :contentReference[oaicite:2]{index=2}

Исходная таблица посещаемости содержит только дни, для которых есть запись.
Поэтому на этапе подготовки данных календарь восстанавливается отдельно для
каждого ресторана в пределах его фактического периода наблюдений. Это позволяет
корректно строить временные признаки и не создавать искусственную историю до
открытия ресторана.

В проекте эти данные объединяются в единую таблицу с ключом
restaurant_id + date, где guests является целевой переменной.

Датасет позволяет проверить подходы, специфичные для временных рядов: недельную сезонность, праздничные
эффекты, лаговые признаки и скользящие статистики, доступна годовая сезонность.


## Baseline

В качестве наивного временного baseline используется значение количества гостей
за аналогичный день предыдущей недели (`lag-7`).

Это позволяет проверить, действительно ли ML-модели дают улучшение относительно
простого сезонного прогноза.

## Baseline

Наивный сезонный прогноз: значение guests за тот же день недели неделю назад
(`lag-7`). Показывает, дают ли ML-модели улучшение относительно простого
сезонного паттерна.

### Модели

**Ridge** — линейная регрессия с L2-регуляризацией. Простая интерпретируемая
модель; L2 снижает влияние мультиколлинеарности и больших коэффициентов при
большом числе признаков после One-Hot Encoding.

**CatBoost** — основная модель. Работает с категориальными признаками без
ручного кодирования, учитывает нелинейные зависимости и взаимодействия между
признаками.

**Prophet** — альтернативный подход к сезонности, без engineered-признаков:
моделирует тренд и сезонность (годовую и недельную) напрямую по ряду.
Обучается отдельно на каждый `restaurant_id`, поэтому сравнивается только на
подвыборке из 5 ресторанов с наибольшей историей — обучение на всех ~829
точках такой архитектурой не укладывается в бюджет задания.

Random Forest исключён из финального сравнения -- рассматривался как подход к нелинейным признакам, 
обучение на всём датасете (OneHotEncoder на 829 категориях `restaurant_id`)
занимает непропорционально много времени.
## Метрики

**MAE** — основная метрика, среднее абсолютное отклонение прогноза в гостях,
интерпретируется напрямую. **RMSE** — дополнительно, сильнее штрафует большие
ошибки. **MAPE** — в процентах, для сопоставимости между ресторанами с разным
потоком.

## Результаты

Полный датасет и подвыборка с Prophet — на разных выборках, отдельные таблицы.

### Полный датасет — 829 ресторанов

| Модель       |      MAE |      RMSE |       MAPE |
| ------------ | -------: | --------: | ---------: |
| **CatBoost** | **6.89** | **11.55** | **60.97%** |
| Ridge        |     7.49 |     11.94 |     66.93% |
| Naive lag-7  |     8.90 |     15.19 |     74.43% |


CatBoost лучший по всем трём метрикам, превосходит бейзлайн.

## Что бы доделала при большом количестве времени

- Prophet сравнить не на 5, а на большем количестве ресторанов, 
  сейчас вывод о его качестве статистически не значимый из-за маленькой выборки.
- Провалидировать `forecast()` не только one-step-ahead на валидации, а на
  честном walk-forward для всего рекурсивного 7-дневного прогноза, который
  реально выдаёт `predict.py`.
- Заменить один фиксированный holdout на `TimeSeriesSplit` с расширяющимся
  окном и `gap` между train/test — имитирует реальную задержку между
  последней известной датой и датой прогноза
  ([разбор техник на Habr](https://habr.com/ru/amp/publications/918832/)).
- Прогноз с интервалом неопределённости (квантильный CatBoost или
  Monte-Carlo), а не точечным значением.
- Учесть длинные серии пропусков (`is_long_gap`) как признак — сейчас они
  просто исключены из target, но не проверено, как их присутствие в истории
  влияет на соседние лаги/rolling.
- Docker, чтобы проект поднимался командой
